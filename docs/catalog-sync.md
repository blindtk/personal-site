# Catalog sync — `github-stars` opens a PR with `content/catalog.json`

`content/catalog.json` (the `/links` catalog and the Lab `stars` command)
is generated by the weekly Action of the private `blindtk/github-stars`
repo. That Action opens (or updates) **a PR here** with that one file; a
human reviews and merges it. This site never fetches anything at build
time: the build imports the vendored JSON statically and fails on a bad
schema (`static/src/lib/catalog.ts`).

```
github-stars (Mon cron) ──generate──▶ catalog/catalog.json
        │ validate shape, build the site with it
        ▼
GitHub App ──▶ branch automation/update-catalog ──▶ PR to main
        │                                           (CI runs, you approve)
        ▼
merge ──▶ Cloudflare Pages builds ──▶ verify-headers runs after deploy
```

## Why a PR, not a push

`main` is behind a ruleset (PR + Code Owners review) and the OpenSSF
Scorecard badge reads the review history: direct bot commits to `main`
count as unreviewed changes and lower the **Code-Review** check. A PR
keeps the ruleset without any bypass actor, runs CI on the exact file,
and the merge is a real review. It is also why the PR is authored by a
GitHub App and not by a person's token: the repo owner can't approve a
PR they authored, but can approve the App's.

The repo is private on the `github-stars` side, so a build-time fetch
would need a read token in Cloudflare Pages and would make every deploy
depend on the GitHub API; the vendored file avoids both.

## One-time setup

1. **Create a GitHub App** (Settings → Developer settings → GitHub Apps
   → New). Name e.g. `github-stars-catalog`; no webhook; homepage = the
   `github-stars` repo URL. Repository permissions: **Contents: Read &
   write**, **Pull requests: Read & write** (Metadata: Read is implied).
   "Where can it be installed": only this account.
2. **Generate a private key** for the App (downloads a `.pem`) and note
   the **App ID**.
3. **Install the App** on this account, restricted to the
   `blindtk/personal-site` repository only.
4. **Secrets in `github-stars`** (Settings → Secrets and variables →
   Actions): `SITE_APP_ID` = the App ID, `SITE_APP_PRIVATE_KEY` = the
   full `.pem` contents. Delete the local `.pem` afterwards.
5. No ruleset change is needed. Check that `automation/**` branches are
   not covered by a ruleset that blocks force-push or creation (the
   `main` ruleset normally targets `main` only).

The `propose-to-site` job lives in `github-stars`'s
`.github/workflows/update-catalog.yml` and runs after the `catalog` job.
It validates the shape (mirrors `assertCatalogShape()` in
`static/src/lib/catalog.ts` — keep the two in step), clones this repo
over HTTPS, copies the one file and **runs `npm run build` with it**.
Only if that passes and the file changed does it mint an installation
token (JWT signed with `openssl`, token limited to this repo, contents +
pull requests), force-push `automation/update-catalog` and open the PR
if none is open. The App key sits in a job-private directory removed on
exit, on the same self-hosted runner as the rest. If last week's PR is
still unmerged, the force-push just refreshes it.

## Failure modes

| What breaks | What happens |
| --- | --- |
| Generator changes the schema | The shape check fails in `github-stars`; no PR is opened. |
| The shape check passes but a nested field breaks the site | The build step fails in `github-stars`; no PR is opened. |
| App not installed on this repo, or wrong secrets | `installation`/token request returns 404/401; the job fails visibly. |
| PR left unmerged | Next run force-pushes the branch; the same PR shows the newest catalog. |
| App key leaked | Delete the key in the App settings and generate a new one; the App can only write to this repo's contents and PRs. |
