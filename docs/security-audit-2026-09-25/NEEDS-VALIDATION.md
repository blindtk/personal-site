# Needs validation

These are prioritised leads with no severity assigned. Each is traced in source, but the decisive fact is outside the repository. Resolve them only through the owner-observed checks listed; **do not send audit traffic to production.**

## Attacker-chosen decoy path length accumulates without bound in the persistent `recent` value and the bucket byPath maps, which may durably break honeypot recording and the threat-intel dashboard

**Fingerprint:** `dynamic/worker/src/index.js:recordHoneypot:unbounded-decoy-path-accumulation`

The '/phpmyadmin/' decoy matches by prefix (decoys.js:23), and the router passes the raw url.pathname to recordHoneypot (index.js:466,482). recordHoneypot stores that path with no length cap or normalization in the event appended to `recent` (up to 200 entries, written with no expirationTtl) and as a byPath key in the hourly and daily buckets. A local run of the real Worker fetch handler against an in-memory fake KV sent 240 decoy requests with ~16 KB paths, spread over 4 simulated days under the global 60/day cap. `recent` grew to 3,218,341 bytes and each hourly/daily bucket to ~961 KB. Every later decoy hit reads and parses `recent` plus two buckets before the cap check. Each accepted hit also re-stringifies them, and the threat-intel refresh parses them and returns ~3.3 MB. In local Node, one parse+stringify of `recent` averaged ~10.3 ms, one further decoy hit took ~12.7 ms and one threat-intel refresh took ~44 ms. That is not Workers CPU accounting. Whether this exceeds the Free-plan per-invocation CPU limit, and whether 16 KB paths reach the Worker through the zone edge, are deployment facts. If the recordHoneypot waitUntil work is killed, `recent` is never rewritten, so the oversized state persists until an operator deletes the key. The buckets expire after 8-9 days. Honest scanner traffic that fits under the cap would slowly push the large entries out of `recent`, but an attacker who spends the shared cap early each UTC day can prevent that.

### Claimed root cause
recordHoneypot builds the event with `path` taken directly from url.pathname (index.js:113-119) and does not cap its length or normalize it to the matched decoy prefix. aggregate.addEvent uses the path as a byPath key (aggregate.js:17). `recent` is rewritten in full on every accepted event with no TTL (index.js:145,157), and it is read and parsed on every decoy hit and on dashboard refreshes (index.js:98,129,243).

### Trace
1. **entrypoint** `dynamic/worker/src/lib/decoys.js:23` (isDecoy): Any path starting with '/phpmyadmin/' counts as a decoy (prefix match), so the path suffix is attacker-controlled and unbounded. The Worker's fetch router calls it with the raw url.pathname (index.js:466,478).
2. **propagation** `dynamic/worker/src/index.js:119` (recordHoneypot): event = { ts, country, asn, path, technique } holds the raw, unbounded path. Only country and asn are normalized.
3. **propagation** `dynamic/worker/src/lib/aggregate.js:17` (addEvent): The path becomes a byPath key in the hourly and daily buckets (called at index.js:146-147).
4. **propagation** `dynamic/worker/src/index.js:145` (recordHoneypot): nextRecent keeps the latest 200 events, each of arbitrary size.
5. **sink** `dynamic/worker/src/index.js:157` (recordHoneypot): env.KV.put('recent', JSON.stringify(nextRecent)) runs with no expirationTtl, so the oversized value persists. It is then read and parsed on every later decoy hit (index.js:129) and on dashboard reads (index.js:98,243).

### Evidence
- `dynamic/worker/src/index.js:128`: Every decoy hit reads `recent` plus the hourly and daily buckets in full, JSON-parsing them before the cap check at index.js:139-140. Over-cap hits therefore also pay the parse cost.
- `dynamic/worker/src/index.js:59`: HONEYPOT_WRITE_CAP = { windowMs: DAY_MS, max: 60 } is one global cap. It limits the accumulation rate (200 entries take ~4 days) but not the size of each entry.
- `dynamic/worker/src/lib/aggregate.js:203`: threatIntel returns up to 200 recent events, so the /api/threat-intel producer (index.js:600-608) serializes the full multi-MB `recent` into its cache value and response. The local run observed a ~3.3 MB body.
- `dynamic/worker/wrangler.toml:138`: The comment records that the Free plan rejects any limits.cpu_ms setting, so the platform's default Free-plan CPU ceiling applies but is not visible in source. The 10 ms figure comes from docs/security-review-2026-07-29.md:179,619.
- `dynamic/worker/src/index.js:482`: recordHoneypot runs inside ctx.waitUntil. A failure is only logged as 'honeypot_write_failed' and there is no self-healing reset of `recent`.

### Blockers
- The deployed maximum URL/path length that the Cloudflare edge accepts for this zone (whether ~16 KB pathnames under /phpmyadmin/* reach the Worker) cannot be observed from source.
- The Workers Free-plan CPU-time enforcement for fetch plus waitUntil work cannot be measured locally, including whether parsing and re-stringifying ~3.2 MB `recent` plus ~1 MB buckets in recordHoneypot, or ~5+ MB in the threat-intel refresh, exceeds it and aborts the write. Local Node (~10 ms per parse+stringify of `recent`, ~12.7 ms per further decoy hit, ~44 ms per threat-intel refresh) is not Workers CPU accounting.

### Resolution plan
- **Local:** Run agents/v-honeypot-path/artifacts/harness.mjs through the sandbox. It imports dynamic/worker/src/index.js, uses an in-memory fake KV, dummy RATE_SALT, a mocked Date.now and the documentation IP 203.0.113.7. It sends 240 GET https://danielmala.co/phpmyadmin/<n>AAAA...(16000 chars) requests over 4 simulated days of 60 each, then records `recent` size, entry count and put TTL, the bucket sizes, the time for one more decoy hit and the time for one /api/threat-intel refresh. Expected output (agents/v-honeypot-path/artifacts/honeypot-path-repro.txt): recent 3,218,341 bytes / 200 entries / TTL null; buckets ~961 KB; threat-intel body ~3.3 MB. To settle the CPU question locally, run the same fixture under `wrangler dev --local` (workerd) with only dummy data and measure the CPU time reported per invocation.
- **Owner-observed:** Owner-only observation, with no audit traffic to production. In Workers Observability logs, look for exceededCpu outcomes or 'honeypot_write_failed' / 'cache_refresh_failed' events. Check the current byte size of the KV key `recent` and the largest d:/h: bucket keys in the dashboard (Storage & Databases → KV → namespace → key). Confirm the zone's effective maximum request-URL length at the Cloudflare edge and whether any WAF rule blocks long /phpmyadmin/* URIs. Do not send oversized decoy requests to production.

## Headers workflow on deployment_status runs code from the deployment commit with repository secrets

**Fingerprint:** `github-workflows-headers.yml:deployment_status-secrets-run-deployment-commit-code`

.github/workflows/headers.yml is triggered by deployment_status. Its only gate is that the deployment state is 'success' (line 24). The job checks out the event's commit (actions/checkout with no ref, line 29), puts secrets ACCESS_CLIENT_ID, ACCESS_CLIENT_SECRET and CI_WAF_TOKEN into the step env (lines 41-46), and runs node .github/scripts/check-headers.mjs from that checkout (line 47). For deployment_status events, GitHub resolves both the workflow file and GITHUB_SHA from the deployment's commit, not from the default branch. The only thing stopping the secrets from going elsewhere is the host allowlist (check-headers.mjs:152 via target.mjs:74). That allowlist is part of the same checked-out code, so it does not protect against a commit that edits the workflow or the script. The workflow never checks deployment.environment, deployment.ref, the creator, or whether the SHA is on main. Suppose the Cloudflare Pages GitHub integration (or any token with deployments:write) creates a successful GitHub deployment for a fork pull-request commit, and GitHub delivers repository secrets to that run. Then a fork author on this public repo could change headers.yml or check-headers.mjs and get the WAF-bypass token and the Access service token. A second path works with the script unchanged: the allowlist trusts every subdomain of personal-site-4fm.pages.dev (target.mjs:31,77). If a fork-PR preview were built with Pages Functions from PR code, that preview would receive x-ci-waf-token and the Access headers. Contributors with write access who push same-repo branches are already trusted, so only fork-originated deployments cross a trust boundary. Whether such deployments exist is hosted configuration and cannot be seen in source.

### Claimed root cause
A secret-bearing job runs on deployment_status, and for that event the code of record (workflow file and checked-out tree) is the deployment commit, not the default branch. Nothing in the workflow checks the deployment environment, ref or SHA. The only secret-destination guard is the in-script allowlist, and the deployment commit supplies that too. The allowlist also trusts all *.personal-site-4fm.pages.dev preview aliases, which may serve PR-built code.

### Trace
1. **entrypoint** `.github/workflows/headers.yml:9` (on.deployment_status): The workflow is triggered by deployment_status events. The file header says the Cloudflare Pages GitHub integration creates these events for Pages deployments. The workflow file and GITHUB_SHA come from the deployment's commit.
2. **propagation** `.github/workflows/headers.yml:29` (jobs.check.steps[0] actions/checkout): actions/checkout has no ref, so it checks out GITHUB_SHA, which is the deployment commit (possibly PR-head code if a deployment is created for it). persist-credentials is false, which limits exposure of GITHUB_TOKEN but not of the step secrets.
3. **propagation** `.github/workflows/headers.yml:41` (jobs.check.steps[1].env): ACCESS_CLIENT_ID, ACCESS_CLIENT_SECRET (lines 41-42) and CI_WAF_TOKEN (line 46) are placed in the step environment. DEPLOY_URL comes from deployment_status.environment_url (line 37).
4. **sink** `.github/workflows/headers.yml:47` (jobs.check.steps[1].run): Runs node .github/scripts/check-headers.mjs from the checked-out deployment commit with the secrets in env. The allowlist decision at check-headers.mjs:152 (isTrustedTarget, target.mjs:74) is enforced only by that same checked-out code.

### Evidence
- `.github/workflows/headers.yml:24`: The only job condition on deployment_status is deployment_status.state == 'success'. There is no check of github.event.deployment.environment, deployment.ref or sha, the creator, or head repository.
- `.github/scripts/check-headers.mjs:138`: The comment (lines 138-145) acknowledges that DEPLOY_URL/environment_url can be set by any app or token with deployments:write, and relies on the in-script allowlist. That allowlist does not help when the script itself comes from untrusted code.
- `.github/scripts/lib/target.mjs:31`: PAGES_PROJECT_HOST is personal-site-4fm.pages.dev. isTrustedTarget (line 77) accepts the host itself and any subdomain, so secrets are sent to every branch/PR preview alias of the project.
- `docs/cloudflare-deploy.md:249`: Section 6 says the repo became public on 2026-07-31 and that the Actions fork-PR permissions checklist was not re-verified. Section 2 (lines 36-40) documents the Pages build config (root static, npm run build) but says nothing about preview or fork build settings for the Pages project.

### Blockers
- Not visible in source: whether Cloudflare Pages project personal-site-4fm builds pull requests from forks and creates GitHub deployments/deployment_status events for those fork commits (preview deployments setting for non-production branches, fork PR handling).
- Not visible in source: whether GitHub runs headers.yml with repository secrets for a deployment_status event whose deployment SHA is a fork-PR head commit (refs/pull/N/head), and whether fork-workflow approval settings or environment protection rules on the Preview environment gate those runs.
- Not visible in source: whether any GitHub App or token other than the Cloudflare integration holds deployments:write on the repo and could create a successful deployment pointing at an attacker-supplied commit.
- Not visible in source: whether the Pages build honours a functions/ directory (static/functions) added by PR code for preview builds, which would let the unmodified allowlist deliver x-ci-waf-token and Access headers to attacker code behind *.personal-site-4fm.pages.dev.

### Resolution plan
- **Owner-observed:** Owner-observed only, with no audit traffic to any deployment. (1) Cloudflare dashboard > Workers & Pages > personal-site-4fm > Settings > Builds: record whether preview deployments are enabled (all non-production branches / custom / none) and whether PRs from forks are built. (2) GitHub > Actions > Headers workflow: list past runs with event=deployment_status and record each run's head SHA, the deployment environment (Production/Preview) and ref. Check whether any SHA is not on main, and whether any came from a fork PR (refs/pull/*/head). (3) GitHub > Settings > Actions > General: record the 'Fork pull request workflows' approval setting. Under Settings > Environments, record whether Preview/Production environments have protection rules or environment-scoped secrets. (4) Settings > Integrations / GitHub Apps: list apps with Deployments write. If any fork-commit deployment reaches this workflow, fix it by gating the job with `if: github.event_name != 'deployment_status' || (github.event.deployment_status.state == 'success' && github.event.deployment.environment == 'Production' && github.event.deployment.ref == 'main')`, or by not exposing CI_WAF_TOKEN/Access secrets to deployment_status runs (scope them to a protected Production environment). Also narrow the target.mjs preview trust so that PR previews do not receive the secrets.
